## 分层不是为了好看

AUTOSAR Classic Platform 把 ECU 软件切成四段：微控制器抽象层（MCAL）、ECU 抽象层、服务层、运行时环境（RTE），最上面是应用层的软件组件（SWC）。

切层的实际收益只有两个：**换芯片只改 MCAL**，**换信号映射只改 Com 配置**。理解了这一点，看那些生成代码才不至于当成黑盒。

## 一次发送的完整路径

一个应用信号要从 SWC 走到总线上，标准路径是：

```
SWC  --(RTE S/R)-->  Com  -->  PduR  -->  CanIf  -->  Can Driver  -->  控制器
```

每一层做的事：

| 层 | 职责 | 典型配置错误 |
| --- | --- | --- |
| RTE | 提供 S/R 与 C/S 接口，隔离 SWC 与 BSW | 接口方向写反，编译过但发送不出去 |
| Com | 把信号打包进 PDU，按发送模式触发 | 周期与主函数周期不对齐，实际周期翻倍 |
| PduR | 路由 PDU，连接 Com / Dcm / CanIf / CanTp | 路由表漏配，诊断能收不能发 |
| CanIf | 管理 HTH/HOH、邮箱与队列 | 邮箱数量不足，突发时丢帧 |
| Can Driver | 写寄存器、启动控制器 | 波特率或采样点与网络不一致 |

## 发送模式决定时序

Com 里每个 PDU 有发送模式：周期、事件、混合。混合模式下，信号变化触发一次立即发送，同时保留周期发送兜底。如果只配了事件、没配周期，接收端在信号不变时永远等不到刷新，会误判为超时。

另外，Com 的主函数 `Com_MainFunctionTx` 必须挂到 OS 任务里，并且任务周期要小于等于最小发送周期的二分之一，否则你会看到“配置 10 ms、实测 20 ms”。

## RTE 的两种通信语义

- **Sender-Receiver**：单向数据，一个 SWC 写、另一个读，不关心谁在读。适合状态类信号。
- **Client-Server**：有请求有响应，带返回值。适合需要确认结果的操作。

两者的差别在于阻塞与超时语义，选错了会在诊断或标定链路上留下难以复现的偶发超时。

## 诊断链路为什么经常配错

诊断请求的路径是 `Dcm -> PduR -> CanTp -> CanIf`，与上面的应用链路在 PduR 处分叉。常见故障是：CanIf 里给诊断配了独立的接收缓冲，但 PduR 里没建对应的路由，结果 ECU 收到了请求、Dcm 却说没收到。

排查顺序永远是：**先看 CanIf 收到没有，再看 PduR 路由有没有命中，最后看 Dcm 服务是否被配置使能**。

## 一句话总结

分层带来的代价是“配置即代码”。同一个功能，写死在 SWC 里两天能跑，正规分层要配五张表。这些表配错的概率远高于代码写错的概率，所以测试的重点应该放在**配置一致性**上，而不是只看功能是否跑通。
