## 一帧报文里有什么

一条经典 CAN 数据帧，抓下来通常长这样：

```
ID: 0x0C0   DLC: 8   DATA: 40 1F 2C FF 00 00 00 00
```

数据段只有 8 个字节，没有任何字段名。谁在哪个位、怎么缩放，全部写在 DBC（或 ARXML）里。所以“解析报文”本质上不是读协议，而是**按信号定义把位重新拼起来**。

## 信号定义决定一切

一个车速信号的典型定义包含六个参数：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 起始位 | 0 | 从数据段第 0 位开始 |
| 长度 | 16 | 占 16 个 bit，两个字节 |
| 字节序 | Intel | 低位在前，低字节在低地址 |
| 缩放因子 | 0.01 | 每个 LSB 代表 0.01 km/h |
| 偏移量 | 0 | 物理值 = 原始值 × 0.01 + 0 |
| 无效值 | 0xFFFF | 该值出现时表示信号不可用 |

按这个定义解：

- `40 1F` 两个字节，Intel 字节序 → 原始值 `0x1F40` = 8000
- 物理值 = 8000 × 0.01 = **80.00 km/h**

如果把字节序当成 Motorola 读成 `0x401F` = 16415，会得到 164.15 km/h——一个在高速上勉强说得通、但在台架上明显不对的数。这类错误最难查，因为它不会崩，只是数值漂。

## 三个高频坑

**字节序**。Intel（小端）从起始位所在字节开始向高字节递增，Motorola（大端）按位编号跨字节排列。同一个信号两种读法差得离谱，而且位跨越字节边界时更容易一起错。

**无效值与默认值**。信号不可用时按定义填全 1（0xFFFF、0xFF），不是 0。把无效值当 0 处理，会出现“车速 0 km/h 但车在跑”的离奇结论。

**有符号与无符号**。温度和扭矩类信号经常是有符号的，长度 8 位、无符号读成 -40 ℃，实际应该是 -40 ℃ 才对——反过来说，把有符号按无符号读，会得到 216 ℃。

## 写成一个能复用的解码函数

```python
def decode_intel(payload, start_bit, length, factor, offset, signed=False):
    byte_i = start_bit // 8
    nbytes = (length + 7) // 8
    raw = int.from_bytes(payload[byte_i:byte_i + nbytes], "little")
    if signed and raw >= (1 << (length - 1)):
        raw -= 1 << length
    return round(raw * factor + offset, 6)

payload = bytes.fromhex("40 1F 2C FF 00 00 00 00")
print(decode_intel(payload, 0, 16, 0.01, 0))   # 80.0
```

注意这段只处理“起始位落在字节边界且整数个字节”的情况。一旦起始位是 bit 3、长度是 12，就必须按位拼装，用掩码逐位取，不能偷懒按字节切。

## 排查顺序

1. 先确认 ID 和 DLC 对得上，别解析了错误的帧；
2. 再确认字节序，方法是用一个已知物理值反推原始值，看两种读法哪个接近真实；
3. 最后确认缩放和无效值。差不多九成的“信号跳变”都停在第二步。
